# 产品定位与判断标准 · 餐谋

> 这份文档不解释产品是什么（那看 PRD），只回答一个问题：
> **这个功能该不该做、做成什么样才算对。**

---

## 1. 用户

代号「舅舅」。**46 岁，跑业务，饭局多，血压高，78 公斤。**

这个画像在 11-18 被修正过一次，修正很关键：

| 旧假设（错） | 现在（对） |
|---|---|
| 50+ 慢病老人 | 40 出头，还在跑业务的中年男性 |
| 最大问题是"不知道方法" | 最大问题是"这周第 4 场"，节奏问题不是单顿问题 |
| 拍照是主要输入 | 一桌客户面前拍照面子成本太高，**能说就不拍** |
| 三餐不规律需要提醒 | 他本来就不规律，按点提醒无效 |
| 热量大头是菜 | 热量大头常常是**酒**，半斤白酒 800–1000 大卡，照片还拍不出来 |

产品同时是用户的求职作品集项目。这不影响功能取舍 —— 但意味着**每个决定都要能讲清理由**，
不能是"网上都这么做"。

---

## 2. 定位与洞察

> **不是热量记账本，是他的饭桌参谋。**

洞察：长辈减不下来，往往不是不知道方法，而是**每顿饭都缺一句"这顿吃对了没"的即时反馈**。

由此推出一件事：**记录是手段，反馈才是产品。** 所以任何让记录变重、让反馈变轻的改动，
方向都是错的。

---

## 3. 五条核心纪律

### D1 每顿必须有一句话

记完一餐只有数字、没有判断，这个产品就没有存在理由。点评按优先级**只取最高的一条**：

| 优先级 | 触发 | 例子 |
|---|---|---|
| P0 | 与疾病冲突 | 「这顿盐有点多，你血压高，下回少放半勺」 |
| P1 | 单顿热量 > 该餐上限 | 「这顿顶了小半天，晚上喝碗粥配个蛋就行」 |
| P1.5 | 单顿合适但当天累计超 | 「这顿没问题，但今天总量已经顶到头了」 |
| P2 | 结构失衡 | 「肉有点少，加个鸡蛋更扛饿」 |
| P3 | 都正常 | 「这顿吃得挺稳，照这个来」 |

**为什么只能一句**：一次说五条，一条都记不住，等于没说。

### D2 运动不换饭

运动消耗**今天不生效**，只进明天预算，而且用**过去 7 天平均**。

理由：如果今晚跑了 40 分钟、环里立刻多 170 大卡，运动就变成了饭的货币。
他会开始"为了多吃去运动"——这跟减重目标正好相反。
用 7 天均值而不是今天的数，是因为今天游了泳不代表明天还游，
单日数会让明天虚高、后天掉回去，他只会觉得软件在抽风。

### D3 永不出现「净摄入」

界面上不能有「吃了 1855 − 动了 300 = 1555」这种算法。
两个数分开摆，中间用一句话说清关系（"这些已经算进明天的预算里了"）。

一出现减法，赎罪逻辑就成立。赎罪是会崩的 —— 崩的那天他会连记录一起放弃。

### D4 超支是事实，不是道德问题

- 不说"你超标了"配红色大字，说"超了 282，明天这样调"。
- 不建议"今晚加练还账"。
- 超 500 大卡以上，建议时长只从 30 加到 45 分钟，并明说"真正的账在饭桌上还，不在这半小时里"。

### D5 用户说了 ≠ 用户吃了

模型对用户的文字描述只能**参考**，不能采纳：
照片里看不到的条目默认**不算热量**，要用户点「我确实吃了」才进账。

理由：随口一句"我还喝了碗汤"，如果能永久改掉这顿饭的账，这个账本就没人信了。

---

## 4. 三条交互纪律

### D6 能点就不打字，但该打字的地方必须有输入框

原 PRD 写的是"零打字"。**这条已经被推翻**（ADR-014），因为：
- 按钮的前提是他先认出"我做的事叫什么"，可他说的是"楼下遛了一圈"；
- 模型会认错菜，认错了不能改，等于让他为模型的错误买单。

现在的规则：**默认路径是点，保底路径是打字和说话，两条都要通。**
判断标准不是"能不能不打字"，而是"他第一次用能不能不学就会"。

### D7 估算永远标「约」，且不装精确

- 热量误差 ±20%，份量误差是最大头（±35%）。
- 所以：不显示小数、不说"你摄入了 1855 大卡"，说"今天 1855"。
- 盐只显示到克（一位小数），**不给毫克**：毫克级的精确感是假的。
- 识别不出来就说"没看清"，不给一个看着像真的数字。

### D8 状态变了，界面必须跟着变

收工之后，环里的话从"还能吃 620"变成"今天吃了 1855"，主按钮从绿色大块换白底小字「再记一顿」。
不这么做的后果：他按了按钮，界面没反应，他会以为没生效，然后再按一次。

## 5. 一个功能做完，用这三问验

1. **他能不能一个人完成？** 需不需要教第二次？（要教第二次就是设计失败）
2. **他知不知道下一步做什么？** 只报数字不给动作 = 没做完。
3. **这个数字他能不能自己验证或反驳？** 说不清怎么算的，他只能信或不信，两种都不好。

三问有一个答不上，就别急着上线。

## 6. 明确不做（含理由）

| 不做 | 理由 |
|---|---|
| 社交 / 排行榜 / 社区 | 单人场景，无网络效应，会稀释核心价值 |
| 食谱库 / 菜谱推荐 | 他吃什么由饭局决定，不由 App 决定 |
| 扫码识别条码 | 目标用户几乎不买带条码的预包装食品 |
| 排便记录 | 记录意愿极低，会把产品拖成"健康日记" |
| 医疗建议 / 诊断 | 合规红线。页脚常驻"仅供参考，不构成医疗建议" |
| 多用户 / 家庭账号 | 先把单用户体验做到极致 |
| 全量食物库 | 中国成品菜没标准配方；误差大头是份量，库救不了（ADR-010） |

## 7. 已被推翻的旧原则（别再照着执行）

| 旧原则（PRD v0.1） | 现状 | 为什么推翻 |
|---|---|---|
| 零打字 | 有菜名编辑、运动输入框、语音 | 模型会错；按钮翻译成本高 |
| 非目标：运动精确记录 | 做了 MET 记录 + 明日建议 | "活动量粗估"用户无法验证，等于让他信一个黑箱 |
| 活动量三选一（没动/走动/锻炼） | 已删 | 选了不影响任何数，是个假按钮 |
| 盐只给档位、不报数字 | 有盐进度条（克） | 光有结论没有刻度，他不知道离 5 克还有多远 |
| 加餐只有"下午茶" | 上午 / 下午茶 / 宵夜 | 20:00 吃的东西叫"下午茶"是荒谬的 |
| 图标替代文字 | 图标只是索引，名词必须写全 | 试过"饭/蛋/油"，用户原话："蛋白质、碳水，怎么能叫饭蛋呢" |
| 超支绝不提"补回来" | 摊到明后天，单日封顶（ADR-016） | 只给"建议骑车 20 分钟"，他心里算得出抵不掉，会判定这软件没用 |
| 运动按钮标默认时长（快走 40 分） | 只写名字，点开再填 | 那个 40 是库里的随手值，看起来像系统建议，照着走完对不上他就不点了 |
| 界面常驻解释文字 | 默认全隐藏，设置里可开 | 默认状态要能单手用完；说明读到第二行他就把手机放下了 |
| 近 7 天按早/午/晚/加四色分层 | 一天一根单色柱，只有"超预算"换色（ADR-018 同期） | 用户原话："这个不是记录一整天的总量吗" —— 四色等于给图装了个要背的图例，而它回答的不是这张图该回答的问题 |
| 每顿之后给下一顿的点评 | 默认关闭，`MEAL_ADVICE_ON` 开关（ADR-019） | 用户原话："太鸡肋了" —— 刚放下筷子就被念"晚饭清一点"，且同一个结论在收工面板里已经说过 |
| 同一个动作按位置换词（加一项 / 再排一项 / 再加一种） | 一律「添加」，名词交给卡片标题（H21、`docs/04` 6.6.1） | 用户第二次强调"能复用的都复用" —— 词表管得住同义词，管不住"换个位置换个词"（K57） |
| 三档速度按"快/中/慢"写死标签 | 按周数排序，最快档等于照这档时不显示"快一点"（ADR-025） | 用户原话："为什么 20 周反而是快一点，不是 17 周最快吗" —— 默认缺口没过安全线，周数按 400 算、预算按 331 算，两个数摆在一张卡上必然打架 |
| 交互区一屏铺满 | 超过三块就二级折叠（H19、`docs/04` 6.8） | 用户原话："这几个屏的交互板块有点多，有点乱" —— 运动页一屏二十来个可点的地方，其中两套输入框长得一模一样 |
| 十七项运动共用十二个图标 | 一项一个，Tabler 取（ADR-020） | 用户原话："这些还是有很多含义不符合" —— 快走和散步都画成脚印，那不是分组，是没画 |

登记表的作用：下次有人（包括我）想"回到更简洁的设计"，先看这里 —— 那些简洁版本已经被否过了。

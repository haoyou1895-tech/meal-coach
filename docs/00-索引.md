## 3. 冲突优先级（重要）

同一个问题，几份材料说法不一样时，按这个顺序取：

1. **线上代码 + 实测结果** —— 事实。代码里怎么写的就怎么算。
2. **`05-决策记录.md`** —— 后写的 ADR 覆盖先写的。这里是"为什么推翻"的存档。
3. **`01-产品定位与判断标准.md`** —— 设计纪律。没被 ADR 推翻的都算数。
4. **`01-PRD-v0.1.md`** —— 2026-11-16 的历史文档，只当背景。**与上面冲突时以 ADR 为准。**
5. **`memory/` 日志** —— 过程记录，不作规范。里面记的是"当时怎么想的"，不是"现在该怎么做"。

> 为什么把 PRD 排这么后：PRD 写的是**当时的假设**，代码是**现在的结论**。
> 这一个月里"零打字""不做运动记录""不做食物库"等条目已经被真实使用推翻了。
> 照着一份过期的假设改代码，是这类项目最容易犯的错。

## 4. 维护规则

| 发生了什么 | 要更新哪份 |
|---|---|
| 加了/改了功能 | `05` 加一条 ADR（哪怕只有三行） |
| 推翻了一条旧决定 | `05` 新增 ADR，并在 `01` 的"已被推翻"表里登记 |
| 踩了新坑 | `06` 加一条带编号的 K |
| 用户提了新的界面要求 | `04` |
| 发了版、换了接口、加了依赖 | `02` |
| 改完一轮 | `07` 划掉做完的 |
| **发了版** | `08` 加一行（编号 + commit + 一句人话），顺手改 `00` 第 1 节 |
| 每周 | `00` 第 1 节的状态表 |

**写 ADR 的门槛要低。** 三行也算：背景一句、决定一句、代价一句。
不写的后果是三个月后有人（包括我自己）把同一个决定再讨论一遍。

## 5. 这套文档不管什么

- 不管代码细节怎么实现 —— 代码自己会说话，注释已经写得很啰嗦。
- 不管 PRD 里的市场分析、指标定义 —— 那些在 `01-PRD-v0.1.md`。
- 不管求职叙事 —— 那属于作品集，不属于工程约束。
